# openai_chat / providers / mistral (Mistral)

Mistral, provider id `mistral`, base URL `https://api.mistral.ai`, `POST /v1/chat/completions` and `GET /v1/models` with `Authorization: Bearer`. API reference: https://docs.mistral.ai/api/ and its OpenAPI document https://docs.mistral.ai/openapi.yaml, read on 2026-10-19; SDK types: `mistralai/client-python` at commit `6229ed96cb5b`.

Every file under `responses/`, `streams/` and `errors/` was recorded live with `cargo xtask record` on 2026-10-19 (`RECORDED.md` in each folder names the request and model). The exception is `errors/greedy-sampling.json`, not recorded: Mistral's body as a Kaeso gateway quoted it whole in its error message when aider sent `requests/greedy-sampling.json` to `mistral-large-4` on 2026-10-24. The requests under `requests/` are written for Mistral: they use its own fields or show what it refuses. `recorded-invalid-api-key` was recorded with a placeholder key. The two files under `models/` are live `GET /v1/models` and `GET /v1/models/ministral-3b-latest` replies; the list keeps 6 of 54 models, unchanged otherwise.

## Chat profile

Mistral rejects every field it doesn't declare with `422 extra_forbidden`. The `chat` profile in `crates/kaeso-core/src/provider.rs` follows these recordings:

| setting | recorded source |
|---|---|
| `max_tokens()` | `errors/recorded-max-completion-tokens-legacy-null`: `max_completion_tokens` is forbidden; `max_tokens` works in every reply here |
| `system_role()` | `errors/recorded-plain-developer-string`: role `developer` is not one of `system`, `user`, `assistant`, `tool` |
| `random_seed()` | `errors/recorded-stop-string-seed-penalties` refuses `seed`; `responses/recorded-safe-prompt-random-seed` takes `random_seed`, which the OpenAPI document gives `minimum: 0` |
| `without_end_user()` | `errors/recorded-user-field`, `errors/recorded-safety-identifier-field` |
| `without_prefill()` | `errors/recorded-assistant-prefill`: a conversation ending with an assistant message is refused (`invalid_request_message_order`); with `prefix: true` Mistral continues it, but `responses/recorded-assistant-prefix` repeats the prefill in its reply, so it can't serve another format's prefill |
| `refusing([...])` | `errors/recorded-function-call-field`, `errors/recorded-functions-field`, `errors/recorded-logit-bias`, `errors/recorded-moderation-field`, `errors/recorded-prompt-cache-options-field`, `errors/recorded-prompt-cache-retention-field`, `errors/recorded-store-field`, `errors/recorded-verbosity-field`, `errors/recorded-web-search-options-field`; `audio` is accepted but `responses/recorded-audio-field` answers it with text only, so it is refused rather than left unanswered. Mistral accepts `metadata`, `modalities` (`responses/recorded-modalities-field`, `["text"]`), `prediction` (`responses/recorded-prediction-doc`), `prompt_cache_key` and `stream_options` (`streams/recorded-stream-include-usage.sse` was recorded with `stream_options.include_usage`, which the gateway sets on every stream) |
| `refusing_in_messages(["name", "refusal"])` | `errors/recorded-system-name-multiturn` (`name` on system and user messages), `errors/recorded-assistant-refusal-field`; `responses/recorded-tool-result-named` shows that a tool message may keep its `name` |
| `greedy_top_p()` | `errors/greedy-sampling`: `temperature: 0` without `top_p` is refused with "top_p must be 1 when using greedy sampling."; the profile sends `top_p: 1` with every `temperature: 0` |
| `thinking_parts()` | `responses/recorded-reasoning-effort-high` and `streams/recorded-reasoning-effort-high-stream`: thinking comes as `{type: "thinking", thinking: [text parts], closed}` parts of `content` |

No Mistral error body has OpenAI's `error` object. The Chat codec reads Mistral's own shapes instead: `{"object": "error", "message": "…", "type", "param", "code"}`, and the validation errors of its OpenAPI document's `HTTPValidationError` (`detail` as a list of `{loc, msg}`, at the top or in `message`) or `detail` as a string. Apps get an error in their own format with Mistral's message; `openai_chat::tests::mistral_error_bodies_reach_apps_with_mistrals_message` checks that instead of the round trip. A bare `{"message": …}` (Mistral's 401 and 429, not recorded) is quoted with its status. No context-window error was recorded, so it reaches apps as an invalid request, not as `ContextTooLong`.

Mistral's profile reads its thinking with `thinking_parts()`: a `thinking` part of a reply's `content` array becomes a `Block::Reasoning`, and in a stream `BlockStart(Reasoning)` with `BlockDelta(ReasoningText)`, while text parts of those arrays become text (`responses/recorded-reasoning-effort-high`, `streams/recorded-reasoning-effort-high-stream`, checked by `openai_chat::tests_thinking`). Apps in another format get it as their own reasoning, with the original block in a reasoning blob. Chat apps get the text as a string `content` and the thinking as `reasoning_content`, never an array: `for-chat-apps/` holds what they get for those two fixtures, which `openai_chat::tests_thinking` compares instead of the round trip. A Chat app's replayed reasoning goes back to Mistral as a `thinking` chunk without `closed`, which defaults to `true`; Mistral's `AssistantMessage.content` (`ContentChunk[]` with `ThinkChunk`) takes it. No request with a replayed `thinking` chunk, alone or next to `tool_calls`, was recorded live. The codec tests that read every fixture without a profile keep the parts as `Unknown` blocks and Extras.

Mistral refuses some values only after the request is sent, because the profile names fields, not values: Chat `file` parts with `file_data` (an Anthropic PDF document becomes one; Mistral's file chunk takes a `file_id`), a `service_tier` other than `auto` or `standard_only` (`errors/recorded-reasoning-cached-usage.json`), and on embeddings OpenAI's `dimensions` and token-id input (`fixtures/openai_embeddings/providers/mistral/errors/`). Apps get Mistral's error, with Mistral's message, in their own format.

No 429 or 5xx body was recorded.
