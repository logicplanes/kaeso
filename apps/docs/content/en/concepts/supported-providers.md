Kaeso has the providers below built in, listed by name. [Providers](providers.md) explains how to use one and what differs between them. An organization can also add a server of its own that speaks one of these formats ([custom providers](../console/custom-providers.md)).

## Columns

- **Provider.** The name the console shows, then the id. The id names the provider in model names, such as `groq/llama-3.3-70b-versatile`, and in [settings](../self-hosting/configuration.md#provider-settings).
- **Formats.** The API formats Kaeso calls the provider with. A model uses the first one unless its **Sends as** value names another ([a model's values](../console/models-and-aliases.md#change-a-models-values)). **Embeddings** and **Gemini Embeddings** mean the provider has embeddings models, which serve `/v1/embeddings`. **Token counts** means it counts tokens for `/v1/messages/count_tokens` and `/v1/responses/input_tokens`.
- **Host.** The host of the provider's default base URL, which the install must reach. A [base URL you set](../self-hosting/configuration.md#provider-settings) replaces it.
- **Key.** Where you create a key, and how the key starts ([provider keys](../console/provider-keys.md)).

## Notes

What else to know about some providers. [Provider profiles](../development/kpp/openai-chat-providers.md#provider-profiles) lists every Chat Completions field a provider renames or refuses:

- **Cerebras.** Cerebras Inference, with models such as `gpt-oss-120b` and `qwen-3.8-27b`. Gets `developer` messages as `system` messages, the end user's id as `user`, the text of a system message that Claude Code or Codex sends after the first turn in the next user turn, and a function without parameters with an empty parameter schema. Grok CLI's replayed `reasoning_content` reaches it as `reasoning`. It refuses a conversation that ends with an assistant message, because Cerebras answers it anew, and a `refusal` on an assistant message. Cerebras answers any field it doesn't know, such as `store`, with 400, and takes images only as data URIs. A model's thinking reaches apps in every format; `gpt-oss-120b` thinks at `reasoning_effort` `low`, `medium` or `high`, `qwen-3.8-27b` also at `none`, and Kaeso refuses other levels.
- **Cohere.** Cohere's [Compatibility API](https://docs.cohere.com/docs/compatibility-api), which covers part of Cohere's own API: documents, citations and rerank aren't reachable through it. Cohere refuses some fields, such as `logit_bias` and `parallel_tool_calls: false`, and gets a single `stop` string as a list. Its reasoning models think at `reasoning_effort` `none` or `high` only. Its Embed models, such as `embed-v4.0`, aren't in KPMR: add them as custom models that send as Embeddings, with their price.
- **DeepSeek.** Gets `developer` messages as `system` messages.
- **Google AI Studio.** The Gemini API of Google AI Studio, with Gemini models such as `gemini-3.5-flash` and `gemini-3.1-pro-preview`, the Gemma models and the embeddings models `gemini-embedding-2` and `gemini-embedding-001`. Kaeso calls it in Gemini's own format with the key in `x-goog-api-key`, so apps in every format reach it and Gemini's thought signatures survive tool calls. Gemini 3 models think at the effort levels KPMR lists for them, sent as `thinkingLevel`. Gemini 2.5 models list none: an Anthropic app's `budget_tokens` goes as `thinkingBudget`, and another app's effort is left out and named in `kaeso-left-out`. Hosted web search is left out, because Gemini's `googleSearch` takes none of its settings. AI Studio keys start with `AIza` or `AQ.`. A key on the free tier has a small daily quota per model; past it, Google answers 429, which apps get as a rate limit. **Check availability** spots a wrong key. Vertex AI, Google Cloud's Gemini API, is not this provider.
- **Groq.** Gets `developer` messages as `system` messages, and refuses some fields, such as `logit_bias`.
- **MiniMax.** MiniMax's Anthropic-compatible API, with `MiniMax-M3` and `MiniMax-M3.1-Flash`, the only models MiniMax serves on it; its M2 models are retired. Kaeso calls it in the Messages format with the key in `x-api-key`, so apps in every format reach it. Kaeso refuses what MiniMax accepts without acting on it: `top_k`, `stop_sequences` (a Chat app's `stop`), `mcp_servers`, `container`, a `temperature` other than 1, a `top_p` other than 0.95 and a `tool_choice` other than `auto`. Claude Code's `context_management` that only clears thinking is left out and named in `kaeso-left-out`. Images go by URL or as base64, and MiniMax refuses documents itself. `MiniMax-M3.1-Flash` always thinks and refuses thinking turned off. MiniMax signs its thinking blocks itself, so an Anthropic app should send a conversation with them only to MiniMax models; Anthropic refuses their signatures. Kaeso refuses token counts, because MiniMax answers them in another shape than Anthropic's. For mainland China, set MiniMax's [base URL](../self-hosting/configuration.md#provider-settings) to `https://api.minimax.cn/anthropic` and use a key from platform.minimax.cn.
- **Mistral.** Gets `developer` messages as `system` messages, and some fields under its own names, such as `seed` as `random_seed`. It refuses others, such as `logit_bias`, and a conversation that ends with an assistant message.
- **Moonshot.** The Kimi API, with Moonshot's Kimi models, such as `kimi-k3` and `kimi-k2.6`. Gets `developer` messages as `system` messages, and an app's prefilled assistant message with Moonshot's `partial: true`, so the reply continues it. It refuses some fields, such as `parallel_tool_calls: false` and `store`, which Moonshot accepts without acting on them. Kimi models fix their sampling: Kaeso refuses a `temperature` other than 1 before sending, and Moonshot refuses other values of `top_p`, `n` and the penalties. A model's thinking reaches apps in every format. The K3 models think at `reasoning_effort` `low`, `high` or `max`, and Kaeso refuses other levels; `kimi-k2.6` stops thinking at `none`, and `kimi-k2.7-code` always thinks. Kimi models refuse `tool_choice: "required"` while they think.
- **Ollama Cloud.** Models that Ollama runs on its own servers, such as `gpt-oss:120b`. Model ids keep Ollama's tag after a colon. Gets every app's output limit as `max_tokens`, because Ollama ignores `max_completion_tokens`, and refuses `logprobs`, `top_logprobs` and `logit_bias`, which Ollama accepts without acting on them. A model's thinking reaches apps in every format. Ollama's free plan includes only some models: for the others Ollama answers 402, which apps get as a refused provider key. Ollama lists its models without checking the key, so **Check availability** can't spot a wrong key; the first request with it reports the refused key. A local Ollama server needs no key; add it as a [custom provider](../console/custom-providers.md) that speaks Chat Completions.
- **OpenAI.** A provider key can also be a ChatGPT account, whose requests use its ChatGPT plan under OpenAI's rules for it ([sign in with a ChatGPT account](../console/provider-keys.md#sign-in-with-a-chatgpt-account)).
- **OpenRouter.** Model ids name the model's maker, such as `anthropic/claude-sonnet-4.5`. Call them as `openrouter/anthropic/claude-sonnet-4.5`, so they never reach the maker's own provider ([how a request names a model](../console/models-and-aliases.md#how-a-request-names-a-model)). Kaeso records costs at the catalogue's prices, not at the `usage.cost` OpenRouter reports. OpenRouter lists its models without checking the key, so **Check availability** can't spot a wrong key; the first request with it reports the refused key.
- **QwenCloud.** Alibaba's model platform outside mainland China, formerly Alibaba Cloud Model Studio, in its Singapore region, with Qwen models such as `qwen3.7-flash` and other makers' models such as `kimi-k3`. A key works only in the region it was created in. For the China (Beijing) region, which KPMR lists as `alibaba-cn`, set QwenCloud's [base URL](../self-hosting/configuration.md#provider-settings) to `https://dashscope.aliyuncs.com/compatible-mode` and use a key from there; an install reaches one region. Gets `developer` messages as `system` messages, and refuses fields QwenCloud accepts without acting on them, such as `logit_bias` and `web_search_options`. An app's thinking reaches the model as `enable_thinking`, an Anthropic app's `budget_tokens` as `thinking_budget`, and a reasoning effort only goes to models that list effort levels, such as `qwen3.8-max`. A Chat app's `max_tokens` limits only the answer, not the thinking; `max_completion_tokens` limits both. Some models only think and refuse thinking turned off, and `qwq-plus` answers only streamed requests: the app gets QwenCloud's 400. Its embeddings models, such as `text-embedding-v4`, aren't in KPMR: add them as custom models that send as Embeddings, with their price.
- **SpaceX.** xAI's API, with models such as Grok. A provider key can also be a Grok account whose plan includes API access, as an experimental option ([sign in with a Grok account](../console/provider-keys.md#sign-in-with-a-grok-account)).
- **Vercel.** Vercel AI Gateway, another gateway whose own routing and fallbacks run behind Kaeso. Model ids name the model's maker, such as `openai/gpt-5-nano`. Call them as `vercel/openai/gpt-5-nano`, so they never reach the maker's own provider ([how a request names a model](../console/models-and-aliases.md#how-a-request-names-a-model)). A model's **Sends as** value can choose Responses or Messages, which Vercel serves too; on Messages, Vercel passes Anthropic's `cache_control` on to Claude models. Kaeso records costs at the catalogue's prices, not at the `usage.cost` Vercel reports, which leaves out Vercel's own surcharges. Vercel counts tokens exactly only for Claude models and estimates the rest, so Kaeso refuses token counts for every Vercel model. Vercel answers for a model without checking the key, so **Check availability** can't spot a wrong key; the first request with it reports the refused key. A Vercel account on the free tier can't call paid models such as Claude: Vercel answers 403, which apps get as a refused provider key, and the request log keeps Vercel's reason.
- **Z.ai.** Z.ai's Anthropic-compatible API, with GLM models such as `glm-5.3` and `glm-4.6`. Kaeso calls it in the Messages format with the key in `x-api-key`, so apps in every format reach it, and an Anthropic app's request goes as the app wrote it. Z.ai documents no list of the Anthropic fields it takes, so Kaeso sends them all and leaves any refusal to Z.ai; Z.ai caches repeated prompts on its own. Z.ai sends its own error codes: an empty balance (`1113`) reaches apps as a refused provider key instead of a rate limit, an overloaded service (`1305`) as overloaded, and a prompt that is too long (`1261`) as one, so Claude Code compacts the conversation. Kaeso refuses token counts, which Z.ai doesn't document. **Check availability** spots a wrong key; Z.ai documents no model listing, so whether it spots a model Z.ai doesn't serve is untested. Z.ai bills each call by the key's type and allows GLM Coding Plan keys only in the coding tools it names, so use a Standard API key. For mainland China, set Z.ai's [base URL](../self-hosting/configuration.md#provider-settings) to `https://open.bigmodel.cn/api/anthropic` and use a key from bigmodel.cn.
