Other providers than OpenAI speak [OpenAI Chat Completions](openai-chat.md) with differences of their own. Look up here how the codec adapts each request to a provider, and what each provider adds, before you add a provider or change its profile.

## Provider profiles

Other providers speak this format with differences of their own. Each provider in `PROVIDERS` (`crates/kaeso-core/src/provider.rs`) names a `kaeso_codecs::openai_chat::ChatProfile` in its `chat` field. The profile holds the provider's name and the settings for the requests Kaeso sends it (`ChatProfile::request`, a `RequestProfile`), set with the builders below.

The gateway hands the profile to the encoder with `EgressCtx::with_chat_profile`, which applies it to every request, whatever format the app sent. `ChatProfile::OPENAI`, the default, changes nothing. `ChatProfile::compatible(name)` differs only in `request.verbosity`, which is false: an OpenAI Responses app's `text.verbosity` is left out instead of sent as `verbosity`, a field only OpenAI documents, which providers that refuse unknown fields would refuse. Custom providers get `ChatProfile::OPENAI.without_verbosity()` for the same reason.

| Setting | What the encoder does | Why it is allowed |
|---|---|---|
| `max_tokens()` | Sends the output limit as `max_tokens`, and a `max_completion_tokens: null` as `max_tokens: null`. A Chat request with both at different values is `Unsupported` (`max_tokens`). | Only the spelling changes; the value is the same. |
| `system_role()` | Sends `developer` messages as `system` messages. | The role spelling is form; both carry the instructions. |
| `random_seed()` | Sends `seed` as `random_seed`, a `seed: null` too. A negative seed, or a request with both `seed` and `random_seed` (either may be `null`), is `Unsupported` (`seed`). The rule follows Mistral's `random_seed`, which its OpenAPI document gives `minimum: 0`. | `seed` stays semantic: it is renamed or refused, never dropped. |
| `end_user_as_user()` | Sends KPP `user` as `user` instead of `safety_identifier`, also when a Chat app sent `safety_identifier`; when a Chat app sent both, `user` carries the id from `safety_identifier`. | Only the key changes; both carry the id of the end user, and `user` is a hint ([field classes](index.md#field-classes)). |
| `without_end_user()` | Leaves KPP `user` out instead of sending it as `user` or `safety_identifier`, together with a second `user` a Chat app sent alongside `safety_identifier`, and their `null` spellings. | `user` is a hint ([field classes](index.md#field-classes)). |
| `without_prefill()` | Refuses a conversation that ends with an assistant message, unless it calls tools or is a Chat app's message with `prefix: true`: `Unsupported` (`assistant prefill`, param `messages[i]`). | A provider that only continues such a message with `prefix: true` repeats the prefill in its reply, so the app would not get a continuation. |
| `without_verbosity()` | Leaves out an OpenAI Responses app's `text.verbosity` instead of sending it as `verbosity`, and names it in `kaeso-left-out`. `compatible(name)` sets it. | `text.verbosity` is a hint ([field classes](index.md#field-classes)). |
| `without_cache_key()` | Leaves out an OpenAI Responses app's `prompt_cache_key` instead of sending it on, and names it in `kaeso-left-out`. | `prompt_cache_key` only routes requests to a prompt cache, and Codex sends it on every request; a provider that refuses the key would refuse every Codex request. |
| `with_message_bookkeeping()` | Sends the bookkeeping keys of a Chat app's assistant messages, `cross::CHAT_ASSISTANT_BOOKKEEPING` (today Grok CLI's `model_id`, also as `null`). Without it, the encoder leaves them out. | The model never reads them, and most Chat providers refuse a message field they don't declare (Groq, Mistral, and OpenAI-compatible proxies), so only a provider known to take them gets them. |
| `tool_patterns(ToolPatterns::Compiled)` | Rewrites the `pattern` keywords of a function tool's parameter schema for a provider that compiles each one and refuses ECMAScript escapes its engine lacks: `\0` becomes `\x00`, a `\b` in a character class `\x08`; a pattern with a named backreference (`\k<name>`) or an empty class (`[]`, `[^]`) is left out of its property. Keys of `patternProperties` are rewritten the same way. The tool is named in `kaeso-adapted`. | The pattern keeps its meaning; the model sees the same constraint written with escapes the provider takes ([DeepSeek](#deepseek)). |
| `tool_schema_root(root)` | Merges a function tool's root union that the provider can't take into one object schema, and names the tool in `kaeso-adapted`; `ToolSchemaRoot::ObjectUnions` keeps a union of inline objects, and `ToolSchemaRoot::TypedObjectUnions` also writes `type: "object"` at a root without a `type`. | The tool, its properties and the model's arguments stay; only the root's shape changes ([union tool schemas](cross-format.md#union-tool-schemas)). |
| `any_audio_format()` | Takes every `input_audio.format` that names a media type ([audio](openai-chat.md#content-parts)); without it, only `wav` and `mp3` (`input_audio_formats`), and other audio is `Unsupported` (`` audio format `flac` ``). | OpenAI's spec lists `wav` and `mp3`; OpenRouter passes any format on to the model's own provider. |
| `with_video_url()` | Sends `Block::Video` as a `video_url` part, a URL or a base64 data URL; without it, video is `Unsupported`. | OpenAI's API has no video part; only providers that document `video_url` get it. |
| `with_tool_parameters()` | Sends `parameters: {"type": "object", "properties": {}}` for a function tool the app sent without `parameters`. | OpenAI reads a function without `parameters` as one without parameters; the empty object schema says the same to a provider that requires the field. |
| `partial_prefill()` | Marks a conversation's final assistant message `partial: true` when an app in another format sent it and it calls no tools, the way Anthropic Messages apps prefill the start of a reply. A Chat app's own messages are sent as written. | The message and its text stay the same; the flag only tells a provider that continues prefills with it, such as Moonshot, to continue the message instead of answering anew and repeating it. |
| `stop_list()` | Sends a single `stop` string as a one-item list. | Only the spelling changes; the stop sequence is the same. A provider that types `stop` as a list refuses the string. |
| `thinking_switch()` | Sends a request's thinking as `enable_thinking`: `false` for thinking turned off or an effort of `none` or `minimal`, which leave `reasoning_effort` out, and `true` otherwise. A budget without an effort goes as `thinking_budget` instead of the effort it maps to; an effort stays `reasoning_effort`. Keys a Chat app sent itself are kept. | The provider switches thinking with its own keys; `reasoning_effort` alone leaves thinking off where the model doesn't think by default. The on/off choice, the budget and the effort reach it unchanged. |
| `leading_system_only()` | Sends the text of system messages that an app in another format placed after the first turn at the start of the next user turn, after its tool results, as for Anthropic Messages ([system messages](cross-format.md#system-messages)); leading ones stay the system prompt. A Chat app's own messages are sent as written. | The text and its order stay; only the role changes. A provider whose models take a system message only at the start, such as Qwen on Cerebras, would refuse the request, and Claude Code and Codex send such messages. |
| `replay_reasoning_as_read()` | Sends the reasoning that a Chat app replays on an assistant message under `reasoning_content` or `reasoning` in the first of `reasoning_fields` when the provider doesn't read the app's key and the message doesn't also carry that one. | The text stays; only the key changes. Grok CLI replays xAI's `reasoning_content` on its assistant turns, which a provider that refuses message keys it doesn't read, such as Cerebras, answers with 400. |
| `greedy_top_p()` | Sends `top_p: 1` whenever the request has `temperature: 0`, whatever `top_p` it set. | At `temperature: 0` the model always takes the most likely token, so `top_p` changes nothing and the app's value is not lost; a provider whose default `top_p` is lower refuses greedy sampling without `top_p: 1`. |
| `refusing(fields)` | Refuses a request whose body would contain one of these top-level keys, such as `` `logit_bias` is not supported by Example Cloud; remove it from the request. `` | Extras are semantic, so they are refused, not dropped. `parallel_tool_calls: true` is the exception: it only allows parallel calls, which a provider without the field allows anyway, so it is left out and named in `kaeso-left-out`. Codex sends it on every request. |
| `refusing_in_messages(fields)` | The same for keys of system, user and assistant messages. Tool messages are not checked. | As above. |

Settings for the replies Kaeso reads (`ChatProfile::reply`, a `ReplyProfile`):

| Setting | What the decoder does | Why it is allowed |
|---|---|---|
| `thinking_parts()` | Reads each part of a `content` array on its own: a text part is text, a `thinking` part (`{type: "thinking", thinking: [chunks], ...}`) a `Block::Reasoning` whose `text` holds its text chunks, with its other keys (`closed`, `signature`) and, when it holds anything but text, its whole `thinking` array in form `thinking`. Other parts (`reference`) are `Block::Unknown`. Streamed thinking becomes `BlockStart(Reasoning)` and `BlockDelta(ReasoningText)`, and a stream keeps other parts and a `thinking` array's other chunks as `BlockStart(Unknown)` blocks ([streams](openai-chat.md#streams-createchatcompletionstreamresponse)); the reasoning block ends when the answer, a refusal or a tool call starts, and a stream's empty text pieces before the first real one open no text block (form `et`). | Chat clients read `content` as a string, so Chat apps never get an array: the text is `content`, the thinking `reasoning_content` (several thinking parts joined by a blank line, none when empty), as from DeepSeek. Other parts, which Chat has no field for, stay in the logged reply only; a stream chunk that carries nothing readable, such as the empty thinking part that closes Mistral's thinking, reaches them without `content`. Text and thinking keep no order between them. Replayed reasoning of a Chat app (`reasoning_content`, `reasoning`, `reasoning_details`) goes back to the provider as `thinking` parts before the text, as do thinking blocks an app in another format sends back; reasoning without readable text is left out. A `thinking` part's `closed` and references don't survive a trip through another format, because a reasoning blob keeps no form. Other formats get the thinking in their own reasoning shape with the original block in a [reasoning blob](reasoning.md#reasoning-blobs). |
| `reasoning_fields(fields)` | Reads the first of these message keys that holds a non-empty string, such as DeepSeek's `reasoning_content` or Groq's `reasoning`, as a `Block::Reasoning` before the reply's other blocks, with form `reasoning_field` naming the key. In a stream, that key of each delta becomes `BlockDelta(ReasoningText)` of one reasoning block, with form `rf` on the chunk. The reasoning block ends when the answer, a refusal or a tool call starts, and empty text pieces before the first real one open no text block (form `et`). An empty string, `null` or another type stays an extra. | Nothing is dropped: Chat apps get the key back as sent, reasoning that an app in another format sends back reaches the provider in the first of these keys, the delta's other keys (Groq's `channel`) stay extras of the chunk, and other formats get the reasoning in their own reasoning shape with the original block in a [reasoning blob](reasoning.md#reasoning-blobs). Without the setting, every streamed piece of reasoning would be a chunk without a KPP event, logged as an unknown block of its own. |
| `error_detail(path)` | Appends the string at this path of an error body, such as OpenRouter's `error.metadata.raw`, to the error's message: `<message>: <detail>`. A missing, empty or non-string value, or one the message already contains, changes nothing. Stream errors get the same. | The body stays as it was: Chat apps get the provider's error unchanged, and other formats get the reason in the message, where a generic one (`Provider returned error`) would tell them nothing. The gateway takes key-like tokens out of every provider error message. |

`refusing` and `refusing_in_messages` each take the whole list; a second call replaces the first. A refusal names the field as the app wrote it. It names a Chat app's key by its own name and path (`logit_bias`, `messages[1].name`), and a refusal block from another format by its KPP path (`messages[1].blocks[0]`).

Refusals happen while the request is encoded, on the request the encoder built and before it is written out. Nothing is sent, and the refusal reaches the app in its own format.

## Providers that use this format

Providers other than OpenAI that serve Chat Completions record into `fixtures/openai_chat/providers/<id>/` ([fixtures](fixtures.md)). Their extra fields follow the rules above; this section names what each one adds. The inference clouds that host open models, such as Fireworks AI and Nebius Token Factory, have a page of their own: [Chat Completions inference clouds](openai-chat-inference-clouds.md).

### DeepSeek

Sources: DeepSeek's [API reference](https://api-docs.deepseek.com/api/create-chat-completion), [thinking mode guide](https://api-docs.deepseek.com/guides/thinking_mode/) and [error codes](https://api-docs.deepseek.com/quick_start/error_codes), read 2026-10-19, and the live recordings in `fixtures/openai_chat/providers/deepseek/`.

| DeepSeek field | KPP | Notes |
|---|---|---|
| `thinking` (request) | extras | Refused when the request goes to another dialect, like other Chat-only fields. |
| `message.reasoning_content`, `delta.reasoning_content` | `Block::Reasoning` | Through the profile's `reasoning_fields`. Chat apps get them back unchanged, and an assistant turn of a Chat app that carries one sends it back to DeepSeek. Anthropic Messages apps get a `thinking` block and Responses apps a reasoning item; when they send it back, it returns to DeepSeek as `reasoning_content` ([reasoning](reasoning.md)), which its thinking mode expects on tool-call turns. |
| `usage.prompt_cache_hit_tokens`, `prompt_cache_miss_tokens` | `raw` usage | The hits equal `prompt_tokens_details.cached_tokens`, which is typed as a cache read. |

| errors in OpenAI's envelope with `code` such as `invalid_api_key`, `model_not_found` or `invalid_parameter_error` | `KppError` | The kind follows the status: 401 for a wrong key, 403 when a free-tier account has used up a model's free quota (`errors/recorded-free-tier-exhausted`), 404 for an unknown model, 400 for the rest, among them a model that only answers streamed requests (`errors/recorded-stream-only-model`). |
| `GET /v1/models`, `GET /v1/models/{model}` | `ModelList`, `ModelInfo` | OpenAI's shape with `owned_by: "system"`, every model in one page with `first_id` `model-id-0`; both refuse a wrong key with 401 (`errors/list-invalid-api-key`). |

QwenCloud also answers OpenAI Responses at `/compatible-mode/v1/responses` and Anthropic Messages at `/apps/anthropic/v1/messages` in this region; only Chat Completions and Embeddings are recorded and listed. A key works only in its own region: the China (Beijing) region is `https://dashscope.aliyuncs.com/compatible-mode`, with its own keys.

### Cerebras

Sources: Cerebras's [Chat Completions reference](https://inference-docs.cerebras.ai/api-reference/chat-completions) and [OpenAI compatibility](https://inference-docs.cerebras.ai/resources/openai) pages, read 2026-11-02, and the live recordings in `fixtures/openai_chat/providers/cerebras/`, made with `gpt-oss-120b` and `qwen-3.8-27b`. Kaeso's base URL is `https://api.cerebras.ai`, which takes `Authorization: Bearer`.

| Cerebras field | KPP | Notes |
|---|---|---|
| `message.reasoning`, `delta.reasoning` | `Block::Reasoning` | Through the profile's `reasoning_fields`, as for Groq. Thinking that an app in another format sends back reaches Cerebras as `reasoning`, which it takes (`responses/recorded-reasoning-sent-back`). A Chat app's `reasoning_content`, such as Grok CLI's, gets 400 from Cerebras, so it goes as `reasoning` too (`replay_reasoning_as_read()`). |
| `time_info`, `system_fingerprint`, `choices[].reasoning_logprobs` | extras | Left out towards other dialects. |
| `completion_tokens_details.accepted_prediction_tokens` and `rejected_prediction_tokens`, `prompt_tokens_details.image_tokens` | `raw` usage | The cached and reasoning tokens are typed as above. |
| `usage` and `time_info` on the finish chunk, also without `stream_options.include_usage` | `Usage` | Cerebras never sends a chunk with `choices: []`. |
| `reasoning_effort` | `reasoning.effort` | `gpt-oss-120b` takes `low`, `medium` and `high`, and `qwen-3.8-27b` also `none`, as KPMR lists; Kaeso refuses other levels before sending, and Cerebras answers them with 400 (`errors/recorded-reasoning-effort-*`). `max_completion_tokens` counts the reasoning. |
| `reasoning_format`, `clear_thinking` (request) | extras | Refused when the request goes to another dialect, like other Chat-only fields. |
| fields Cerebras doesn't declare, such as `safety_identifier`, `metadata`, `store` or `web_search_options` | sent | Cerebras answers 400 `property '…' is unsupported`, which reaches the app. The profile sends the end user's id as `user` (`end_user_as_user()`), so Claude Code's `metadata.user_id` arrives there. |
| `logit_bias`, `logprobs`, `top_logprobs`, both penalties, `seed`, `stop`, `prompt_cache_key`, `parallel_tool_calls`, `service_tier`, `prediction` | sent | Cerebras takes them (`responses/recorded-logit-bias-honoured` shows the bias at work). A `stop` sequence also ends the reasoning, which can leave a reply without `content` (`responses/recorded-sampling`). |
| the `developer` role, a `system` message after the first turn | `Role::System` | Qwen's chat template refuses both with 400. `system_role()` sends `system`, and `leading_system_only()` moves the text of a later system message from an app in another format, such as Claude Code or Codex, into the next user turn. |
| a final assistant message | refused | Cerebras answers it anew and repeats it (`responses/recorded-prefill`), so `without_prefill()` refuses it before sending. |
| `refusal` on an assistant message, also `null` | refused | Cerebras answers 400 (`errors/recorded-assistant-refusal`); the profile refuses it before sending. |
| a function without `parameters` | `parameters` | `with_tool_parameters()` sends the empty object schema that `gpt-oss-120b`'s chat template requires (`errors/recorded-tool-without-parameters`). |
| `tools` together with `response_format` on `gpt-oss-120b`, an image as an `https` URL or to a model without images | sent | Cerebras answers 400 (`errors/recorded-tools-with-response-format`, `errors/recorded-image-url`, `errors/recorded-image-gpt-oss`), which reaches the app. |
| errors with OpenAI's `message`, `type`, `param` and `code` at the top level, without the `error` object | `KppError` | The message and `param` are Cerebras's, and the kind follows the status: a wrong key (401 `wrong_api_key`) is a refused key, and the account's tokens-a-minute limit (429 `too_many_tokens_error`, `retry-after: 60`) a rate limit. Chat apps get the error in OpenAI's shape. |
| `GET /v1/models` | `ModelList` | The models the key may call, with `created: 0` and `owned_by: "Cerebras"`; a wrong key gets 401, so a model check spots it. |

Cerebras has no Responses, Messages, embeddings or token-count endpoint (all answer 404), so `embeddings` and `count_tokens` are `None`.
